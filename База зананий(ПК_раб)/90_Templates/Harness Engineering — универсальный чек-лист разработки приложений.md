# Harness Engineering — универсальный чек-лист разработки приложений

Шаблон для проектов, где AI-агент пишет, проверяет или сопровождает код. Подходит для web, mobile, desktop, backend, data/ML и внутренних инструментов.

> Цель harness: не «дать модели хороший промпт», а создать управляемую систему вокруг неё — контекст, рабочий цикл, состояние, инструменты, ограничения, проверки и обратную связь.

Основано на заметке [[Harness Engineering — транскрипт видео]]. Дополняет шаблон [[Универсальный чек-лист среды проекта с AI-агентом]]: существующий шаблон отвечает преимущественно за подготовку среды, а этот — за полный жизненный цикл агентной разработки и улучшение harness.

## 1. Цель и критерии готовности

- [ ] Проблема сформулирована одним абзацем без описания заранее выбранного решения.
- [ ] Определён пользователь и его ожидаемый результат.
- [ ] Записаны функциональные требования.
- [ ] Записаны нефункциональные требования: производительность, безопасность, доступность, совместимость, стоимость.
- [ ] Указано, что не входит в задачу.
- [ ] Критерии приёмки наблюдаемы и проверяемы.
- [ ] Для каждого критерия указан способ проверки: тест, сценарий, метрика или ручной осмотр.
- [ ] Определено условие остановки: когда агент обязан считать работу завершённой.

## 2. Контекст проекта

- [ ] Агенту даны актуальные инструкции проекта (`AGENTS.md`, README, правила стиля).
- [ ] Перечислены ключевые директории и точки входа.
- [ ] Указаны версии языка, фреймворка, runtime и пакетного менеджера.
- [ ] Описана архитектура и границы модулей.
- [ ] Приведены существующие паттерны, которые нужно повторять.
- [ ] Перечислены команды установки, запуска, тестирования, lint и сборки.
- [ ] Известные ограничения и технический долг отделены от требований текущей задачи.
- [ ] Секреты заменены именами переменных и никогда не помещаются в контекст открытым текстом.
- [ ] Контекст минимален: исключены большие логи, нерелевантные файлы и устаревшие документы.

## 3. Рабочий процесс агента

- [ ] Процесс зафиксирован как последовательность: понять → исследовать → спланировать → изменить → проверить → отрецензировать → отчитаться.
- [ ] Перед изменениями агент проверяет текущее состояние проекта и незакоммиченные изменения.
- [ ] Для неопределённостей задано правило: исследовать локально, затем сделать безопасное допущение или запросить решение.
- [ ] Крупная задача разбита на проверяемые этапы.
- [ ] После каждого этапа есть дешёвая проверка, не только финальный прогон.
- [ ] Определены лимиты повторных попыток и признаки зацикливания.
- [ ] Есть правило отката или прекращения работы при ухудшении результата.
- [ ] Финальный отчёт включает изменения, проверки, ограничения и оставшиеся риски.

## 4. Состояние и память

- [ ] Есть единый источник истины для плана и статуса.
- [ ] Зафиксированы принятые решения и их причины.
- [ ] Агент сохраняет только устойчивые знания, полезные для следующих запусков.
- [ ] Временные наблюдения не смешиваются с постоянными инструкциями.
- [ ] Состояние переживает перезапуск: файл, issue, БД или журнал запуска.
- [ ] Указаны владелец, срок жизни и правила очистки сохранённого состояния.
- [ ] Память не содержит секретов, персональных данных и лишних пользовательских данных.
- [ ] Перед использованием старой памяти проверяется её актуальность.

## 5. Инструменты и разрешения

- [ ] Агенту доступны только инструменты, необходимые для задачи.
- [ ] Для каждого инструмента понятно: читать, писать, запускать, публиковать или удалять.
- [ ] Разрешения следуют принципу минимальных привилегий.
- [ ] Чтение отделено от действий с внешними последствиями.
- [ ] Опасные действия требуют подтверждения человека: production, платежи, права доступа, публикация, удаление данных.
- [ ] Цели файловых операций ограничены явными директориями.
- [ ] Сетевой доступ ограничен нужными доменами.
- [ ] Установлены лимиты времени, стоимости, запросов и параллелизма.
- [ ] Ошибки инструментов обрабатываются явно; агент не повторяет действие бесконечно.

## 6. Песочница и воспроизводимость

- [ ] Работа выполняется в изолированной среде: dev container, VM, sandbox или отдельный workspace.
- [ ] Среда поднимается одной документированной командой.
- [ ] Зависимости закреплены lock-файлом.
- [ ] Используются тестовые или синтетические данные.
- [ ] Production-учётные данные недоступны по умолчанию.
- [ ] Миграции и разрушительные операции сначала прогоняются на копии.
- [ ] Зафиксированы версия образа, ОС и внешние сервисы.
- [ ] Артефакты запуска можно воспроизвести: команды, логи, отчёты, версии.

## 7. Роли, субагенты и параллельная работа

- [ ] Делегирование используется только для независимых и чётко ограниченных задач.
- [ ] У каждой роли есть вход, ожидаемый выход и критерии завершения.
- [ ] Исполнитель и проверяющий разделены.
- [ ] Проверяющий по умолчанию не может менять код.
- [ ] Владение файлами между параллельными исполнителями не пересекается.
- [ ] Формат передачи результата стандартизирован: вывод, доказательства, риски, файлы.
- [ ] Главный агент проверяет вывод субагента, а не принимает его на веру.
- [ ] Есть правило разрешения конфликтов и единый интегратор результата.

## 8. Проверки и evals

- [ ] До начала работы зафиксирован baseline: текущее поведение, тест или метрика.
- [ ] Есть автоматические проверки требований, где это возможно.
- [ ] Пройдены unit-тесты затронутой логики.
- [ ] Пройдены integration/API-тесты на границах модулей.
- [ ] Проверен основной пользовательский сценарий end-to-end.
- [ ] Проверены негативные сценарии, пустые состояния и ошибки внешних сервисов.
- [ ] Проверены безопасность, права доступа и валидация входных данных.
- [ ] Проверены производительность и ресурсы для критичных путей.
- [ ] UI проверен визуально, включая responsive и accessibility, если применимо.
- [ ] Миграции проверены вперёд и, если требуется, назад.
- [ ] Новые тесты действительно падают без исправления.
- [ ] Результат сравнивается с baseline и критериями приёмки, а не с субъективным «выглядит хорошо».
- [ ] Независимый reviewer/evaluator выдал структурированную оценку.

## 9. Наблюдаемость

- [ ] Логи содержат этап, действие, длительность и результат без секретов.
- [ ] Ошибки различают проблему продукта, среды, инструмента и модели.
- [ ] Сохраняются версии модели, промпта, workflow и набора evals.
- [ ] Измеряются время, стоимость, число итераций и доля успешных проверок.
- [ ] Для production определены метрики здоровья, алерты и владелец реакции.
- [ ] По журналу можно восстановить, почему агент принял ключевое решение.

## 10. Безопасность и данные

- [ ] Выполнено моделирование угроз для новых поверхностей атаки.
- [ ] Недоверенный контент не может изменять системные инструкции агента.
- [ ] Входы, файлы и ответы внешних систем валидируются.
- [ ] Секреты не попадают в промпты, логи, тестовые фикстуры и коммиты.
- [ ] Персональные данные минимизированы и имеют законный срок хранения.
- [ ] Зависимости и контейнеры проверены на известные уязвимости.
- [ ] Лицензии новых зависимостей совместимы с проектом.
- [ ] Есть безопасный путь отката, отключения функции или kill switch.

## 11. Самоулучшение — с ограничителями

- [ ] После запуска агент фиксирует проблемы, обратную связь и успешные приёмы.
- [ ] Каждое обучение классифицировано: проектное, технологическое или универсальное.
- [ ] Для каждого урока записано, как обнаружить похожую ситуацию в будущем.
- [ ] Урок сформулирован как конкретная исполнимая инструкция.
- [ ] Временные и узкие наблюдения не превращаются в глобальные правила.
- [ ] Новое правило сопровождается примером или eval, подтверждающим пользу.
- [ ] Самоизменение workflow выполняется отдельным diff и проходит review.
- [ ] Агент не может сам расширять свои права, бюджет или область доступа.
- [ ] Рекурсивное самоулучшение ограничено: предлагаются изменения метода улучшения, но их утверждает человек.
- [ ] Устаревшие и конфликтующие правила регулярно удаляются.
- [ ] После записи улучшений агент перечитывает итоговый workflow и проверяет непротиворечивость.

## 12. Подготовка к релизу

- [ ] Все критерии приёмки подтверждены доказательствами.
- [ ] CI зелёный, сборка воспроизводима.
- [ ] Изменения данных и конфигурации задокументированы.
- [ ] Обновлены пользовательская и эксплуатационная документация.
- [ ] Определены rollout, feature flag, canary или поэтапное включение.
- [ ] Есть rollback-план и ответственный.
- [ ] Мониторинг после релиза настроен до публикации.
- [ ] Известные ограничения и ручные шаги переданы владельцу.
- [ ] Человек одобрил действия с внешними последствиями.

## 13. Финальный gate

Запуск можно считать завершённым, только если все обязательные пункты ниже отмечены:

- [ ] Scope соблюдён; нет случайных изменений.
- [ ] Критерии приёмки выполнены.
- [ ] Проверки пройдены и перечислены.
- [ ] Независимая проверка завершена.
- [ ] Критические и высокие риски устранены или явно приняты владельцем.
- [ ] Безопасность, данные и разрешения проверены.
- [ ] Документация и журнал решений обновлены.
- [ ] Релиз и откат понятны.
- [ ] Улучшения harness предложены отдельным, проверяемым изменением.

## Минимальная версия для небольшой задачи

- [ ] Ясная цель и критерии приёмки.
- [ ] Ограниченный scope файлов и разрешений.
- [ ] Короткий план с проверкой после каждого этапа.
- [ ] Изолированная воспроизводимая среда.
- [ ] Автотесты плюс проверка основного пользовательского сценария.
- [ ] Независимый review результата.
- [ ] Финальный отчёт с доказательствами и рисками.
- [ ] Один проверяемый урок для улучшения следующего запуска.
