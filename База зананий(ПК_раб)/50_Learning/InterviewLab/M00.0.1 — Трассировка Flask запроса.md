# M00.0.1 — Трассировка одного Flask-запроса

## Задача

Не вспоминать определения, а проследить один конкретный запрос:

```text
GET /health → Waitress → app.wsgi_app → Flask → health view → response
```

Предположим:

- запущен один Python process;
- Waitress настроен на четыре worker threads;
- один пользователь отправил `GET /health`;
- view выполняется синхронно.

## Рабочая модель

Это готовая схема для изучения, а не таблица для заполнения.

| Событие | Где происходит | Что это означает |
|---|---|---|
| Windows запускает сервер | Process | Создаётся отдельная память, PID, CPython и главный thread |
| Сервер импортирует `wsgi.py` | Главный thread процесса | Выполняется top-level код модуля |
| Выполняется `from app import app` | Тот же process и thread | При первом импорте выполняется top-level код `app.py` |
| Waitress получает HTTP-запрос | Серверный I/O-механизм | Запрос разбирается и готовится для WSGI |
| Запрос получает worker thread | Один из четырёх threads | Этот thread занят запросом до завершения WSGI-вызова |
| Вызывается `app.wsgi_app` | Worker thread | Flask получает WSGI `environ` и `start_response` |
| Flask создаёт request context | Worker thread | `request`, `session`, `g` указывают на данные этого запроса |
| Выполняется health view | Worker thread | Обычный синхронный Python-код выполняется в текущем thread |
| View ждёт синхронный запрос к БД | Тот же worker thread | Thread остаётся занят, но другие свободные threads могут работать |
| Flask возвращает response | Worker thread → Waitress | Context очищается, thread освобождается для следующего запроса |

## Один запрос своими словами

Допишите окончания:

1. Если все четыре worker threads ждут медленную БД, пятый запрос может работать

## Разбор преподавателя — 2026-08-13

### Что понято правильно

- Waitress находится перед Flask и принимает HTTP-запрос;
- запрос передаётся worker thread;
- Flask создаёт request context и вызывает view function;
- во время синхронного запроса к БД worker thread остаётся занят;
- после формирования response thread можно использовать для другого запроса.

### 1. Process создаётся не для каждого запроса

Запуск сервера и обработка запросов — два разных этапа:

```text
Один раз при старте:
Windows → Python process → импорт wsgi.py и app.py → запуск Waitress

Много раз после старта:
браузер → уже работающий Waitress → worker thread → Flask → response
```

Один process обслуживает множество запросов. Новый process для каждого `GET /health` не создаётся.

### 2. WSGI `environ`

`environ` — Python-словарь, в который Waitress помещает входные данные в стандартном WSGI-формате:

```python
environ = {
    "REQUEST_METHOD": "GET",
    "PATH_INFO": "/health",
    "QUERY_STRING": "",
    "SERVER_NAME": "localhost",
    "SERVER_PORT": "5002",
    "REMOTE_ADDR": "127.0.0.1",
    "wsgi.input": ...,  # поток с телом запроса
}
```

Flask читает `environ`, создаёт удобный объект `request` и выбирает маршрут.

### 3. WSGI `start_response`

`start_response` — функция, которую Waitress передаёт Flask. Flask вызывает её, чтобы сообщить статус и headers ответа:

```python
start_response(
    "200 OK",
    [("Content-Type", "application/json")],
)
```

Затем Flask возвращает body. Waitress собирает статус, headers и body в HTTP-response и отправляет браузеру.

Упрощённое WSGI-приложение выглядит так:

```python
def application(environ, start_response):
    path = environ["PATH_INFO"]
    start_response("200 OK", [("Content-Type", "text/plain")])
    return [f"Requested: {path}".encode()]
```

### 4. Threads одного process делят память

Threads имеют отдельные стеки выполнения, но используют общий heap процесса. Поэтому два threads видят один глобальный словарь. Именно совместное изменение создаёт race condition:

```text
Thread A читает counter = 10
Thread B читает counter = 10
Thread A записывает 11
Thread B записывает 11
```

Ожидалось `12`, получилось `11`: одно обновление потеряно. База данных может быть правильным местом хранения, но там всё равно нужны транзакции, блокировки или атомарные запросы.

### 5. Processes имеют раздельную память

У каждого process своё адресное пространство, CPython и GIL. После импорта каждый process получает независимую копию глобального словаря:

```text
Process A: cache = {"value": 1}
Process B: cache = {"value": 1}

Process A меняет value на 2
Process B продолжает видеть value = 1
```

Для общего состояния используют PostgreSQL, Redis или механизм межпроцессной коммуникации.

### 6. Все worker threads заняты

Если все четыре worker threads ждут БД, пятый готовый запрос ждёт в очереди Waitress, пока один thread не освободится. При слишком долгом ожидании клиент или proxy может получить timeout.
