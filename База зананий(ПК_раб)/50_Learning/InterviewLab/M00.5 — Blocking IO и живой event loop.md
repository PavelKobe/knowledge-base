# M00.5 — Blocking I/O и живой event loop

## Цель

Понять главное правило async backend:

> Код внутри `async def` должен регулярно возвращать управление event loop. Синхронная блокирующая функция этого не делает.

В [[M00.4 — Последовательный и конкурентный await]] две Task работали конкурентно, потому что `asyncio.sleep()` добровольно отдавал управление.

Теперь сравним его с `time.sleep()`.

## 1. Пульс event loop

Представим Task, которая печатает пульс каждые 0,2 секунды:

```python
async def heartbeat() -> None:
    for number in range(1, 4):
        print(f"пульс {number}")
        await asyncio.sleep(0.2)
```

Если пульс появляется регулярно, event loop продолжает получать управление.

Если пульс замер, значит какой-то код удерживает thread event loop и не позволяет переключиться.

## 2. Блокирующее ожидание

```python
async def blocking_work() -> None:
    print("blocking: старт")
    time.sleep(0.6)
    print("blocking: финиш")
```

`time.sleep(0.6)` говорит операционной системе приостановить текущий thread.

В базовой модели asyncio этот thread одновременно является thread, где работает event loop. Пока он спит:

- event loop не исполняет Python-код;
- другие Task не получают управление;
- heartbeat не печатает новые строки;
- запросы этого ASGI worker могут задерживаться.

Наличие `async def` вокруг `time.sleep()` не исправляет ситуацию.

## 3. Неблокирующее ожидание

```python
async def nonblocking_work() -> None:
    print("async: старт")
    await asyncio.sleep(0.6)
    print("async: финиш")
```

`await asyncio.sleep(0.6)` приостанавливает текущую Task, а не thread.

```text
Task nonblocking_work → ждёт таймер
event-loop thread     → свободен выполнять heartbeat
```

После готовности таймера Task снова попадает в очередь готовых Task.

## 4. Связь с реальным backend

Та же проблема возникает с синхронными библиотеками:

```python
@app.get("/external")
async def external():
    response = requests.get("https://example.com")
    return response.json()
```

`requests.get()` ожидает сеть синхронно. Event loop не получает от библиотеки awaitable и не может переключить текущую Task.

Аналогичные примеры:

- синхронный драйвер PostgreSQL внутри `async def`;
- обычный `time.sleep`;
- синхронное чтение очень большого файла;
- некоторые SDK внешних сервисов;
- тяжёлое CPU-вычисление без `await`.

## 5. Основные решения

### Решение A. Использовать async-библиотеку

```python
response = await httpx_client.get(url)
```

Для PostgreSQL:

```python
result = await async_session.execute(statement)
```

Это основной вариант для I/O внутри async-приложения.

### Решение B. Адаптировать sync I/O через thread pool

```python
result = await asyncio.to_thread(sync_function)
```

Синхронная функция выполняется в другом thread. Event-loop thread остаётся свободным.

Это адаптер, а не превращение функции в настоящую async-функцию. Thread pool ограничен, а отмена Task не всегда способна немедленно остановить уже работающую sync-функцию.

### Решение C. Использовать обычный `def` endpoint

FastAPI/Starlette выполняет обычные sync endpoints в thread pool:

```python
@app.get("/legacy")
def legacy():
    return sync_sdk.load_data()
```

Это допустимо, если весь стек endpoint синхронный. Но thread pool остаётся ограниченным ресурсом.

### Решение D. Вынести работу наружу

Если операция:

- долгая;
- обязательная;
- должна пережить перезапуск API;
- требует retry;

её выносят в RabbitMQ и отдельный worker.

Для тяжёлого Python CPU-кода также нужен отдельный process/worker, а не просто `asyncio.to_thread`.

## 6. Практическое наблюдение

Создайте временный файл `blocking_observation.py`:

```python
import asyncio
import time


async def heartbeat(label: str) -> None:
    for number in range(1, 4):
        print(f"{label}: пульс {number}")
        await asyncio.sleep(0.2)


async def blocking_work() -> None:
    print("blocking: старт")
    time.sleep(0.6)
    print("blocking: финиш")


async def nonblocking_work() -> None:
    print("async: старт")
    await asyncio.sleep(0.6)
    print("async: финиш")


async def blocking_demo() -> None:
    print("--- blocking demo ---")
    async with asyncio.TaskGroup() as group:
        group.create_task(heartbeat("blocking"))
        group.create_task(blocking_work())


async def nonblocking_demo() -> None:
    print("--- async demo ---")
    async with asyncio.TaskGroup() as group:
        group.create_task(heartbeat("async"))
        group.create_task(nonblocking_work())


async def main() -> None:
    await blocking_demo()
    await nonblocking_demo()


asyncio.run(main())
```

## Разбор преподавателя — 2026-08-17

### Исправление прогноза

`time.sleep(0.6)` не передаёт управление event loop. Он блокирует OS thread, в котором работает loop. Поэтому после `blocking: старт` пульсы 2 и 3 появились только после `blocking: финиш`.

В предварительном третьем ответе была указана одна Task, но фактический результат показал блокировку всего event-loop thread. Следовательно, ни одна Task этого loop не могла исполняться.

### Что подтверждено после запуска

- синхронная функция внутри `async def` остаётся синхронной;
- две созданные Task не помогают, если одна удерживает единственный event-loop thread;
- `requests.get()` внутри async endpoint блокирует loop;
- основной вариант для HTTP — async-клиент вроде `httpx.AsyncClient`;
- sync SDK при необходимости адаптируется через ограниченный thread pool.
