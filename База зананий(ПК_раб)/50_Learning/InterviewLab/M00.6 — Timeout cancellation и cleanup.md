# M00.6 — Timeout, cancellation и cleanup

## Цель

Понять три связанных механизма:

```text
timeout → запрос на отмену Task → CancelledError → cleanup в finally
```

## 1. Почему нужен timeout

Внешний сервис может:

- отвечать слишком долго;
- зависнуть;
- потерять соединение;
- принять запрос, но не вернуть ответ.

Без ограничения времени Task может ждать неопределённо долго и удерживать ресурсы:

- соединение с БД;
- место в connection pool;
- память;
- пользовательский запрос;
- lock или semaphore.

Timeout — верхняя граница допустимого ожидания.

## 2. Простая аналогия

Представим сотрудника, который выполняет задачу, и будильник:

```text
Task            → сотрудник
asyncio.timeout → будильник
CancelledError  → сигнал «остановись»
finally         → убрать стол и вернуть ключи
TimeoutError    → сообщение руководителю «время закончилось»
```

Будильник не уничтожает сотрудника физически. Он подаёт сигнал отмены. Coroutine получает этот сигнал в подходящей точке `await` и должна корректно освободить ресурсы.

## 3. Как работает `asyncio.timeout`

```python
try:
    async with asyncio.timeout(2):
        result = await external_call()
except TimeoutError:
    print("Сервис не ответил за 2 секунды")
```

Упрощённая последовательность:

```text
1. Task входит в timeout-блок.
2. Запускается external_call().
3. Task доходит до незавершённого await.
4. Проходит две секунды.
5. asyncio запрашивает отмену текущей Task.
6. В coroutine возникает CancelledError.
7. Выполняются finally-блоки.
8. Контекст timeout преобразует внутреннюю отмену в TimeoutError.
9. Внешний except TimeoutError обрабатывает превышение времени.
```

`TimeoutError` ловится снаружи `async with`, потому что преобразование происходит при выходе из timeout-контекста.

## 4. Cancellation — запрос, а не мгновенное убийство

```python
task.cancel()
```

`cancel()` просит Task отмениться. На ближайшей подходящей точке выполнения, обычно `await`, в ней возникает `asyncio.CancelledError`.

Почему отмена не всегда мгновенная:

- Task может выполнять CPU-код без `await`;
- event-loop thread может быть заблокирован sync-функцией;
- coroutine сначала выполняет cleanup;
- sync-функция, уже отправленная в thread pool, может продолжить работу.

Если event loop заблокирован через `time.sleep`, он даже не может своевременно доставить сигнал отмены.

## 5. Зачем нужен `finally`

`finally` выполняется при обычном завершении, исключении и cancellation:

```python
async def use_resource() -> None:
    resource = await open_resource()
    try:
        await work(resource)
    finally:
        await resource.close()
```

В `finally` обычно:

- закрывают соединения;
- возвращают соединение в pool;
- освобождают lock;
- удаляют временный файл;
- завершают транзакцию rollback;
- прекращают дочерние операции.

Cleanup должен выполняться даже тогда, когда полезный результат не получен.

## 6. Почему нельзя молча проглатывать `CancelledError`

Проблемный код:

```python
async def work() -> None:
    try:
        await long_operation()
    except asyncio.CancelledError:
        print("Меня попросили отмениться, но я продолжу")
        # Ошибка: исключение не передано выше
```

Task получила запрос завершиться, но coroutine скрыла его. Это может нарушить:

- timeout;
- `TaskGroup`;
- graceful shutdown приложения;
- остановку запроса после отключения клиента.

Корректный шаблон, если нужно залогировать отмену:

```python
async def work() -> None:
    try:
        await long_operation()
    except asyncio.CancelledError:
        print("Task отменяется")
        raise
    finally:
        print("Освобождаем ресурсы")
```

`raise` повторно передаёт тот же `CancelledError` вызывающему коду.

Часто отдельный `except CancelledError` вообще не нужен: достаточно cleanup в `finally`.

## 7. Timeout не равен retry

Timeout отвечает на вопрос:

> Сколько времени разрешено одной операции или блоку операций?

Retry отвечает на другой вопрос:

> Нужно ли повторить операцию после определённой ошибки?

Нельзя автоматически повторять любую операцию. Например, платёж мог пройти, хотя ответ потерялся. Повтор без idempotency key способен списать деньги второй раз.

Retry требует:

- ограниченного числа попыток;
- backoff;
- общего временного бюджета;
- фильтра повторяемых ошибок;
- идемпотентности.

## 8. Практическое наблюдение

Создайте файл `timeout_observation.py`:

```python
import asyncio


async def use_resource() -> None:
    print("ресурс: открыт")
    try:
        for step in range(1, 6):
            print(f"работа: шаг {step}")
            await asyncio.sleep(0.2)
    except asyncio.CancelledError:
        print("работа: получен CancelledError")
        raise
    finally:
        print("ресурс: закрыт в finally")


async def main() -> None:
    try:
        async with asyncio.timeout(0.45):
            await use_resource()
    except TimeoutError:
        print("main: получен TimeoutError")

    print("main: программа продолжилась")


asyncio.run(main())
```

## Разбор преподавателя — 2026-08-17

### 1. Сколько шагов выполнилось

Фактически напечатаны шаги 1, 2 и 3:

```text
t=0.00  печатается шаг 1, затем await sleep
t=0.20  печатается шаг 2, затем await sleep
t=0.40  печатается шаг 3, затем await sleep
t=0.45  timeout запрашивает отмену во время ожидания
```

Шаг 4 не начался.

### 2. Какие исключения видны на разных уровнях

Внутри `use_resource()` возникает `CancelledError`. Это сигнал текущей Task прекратить выполнение.

Далее происходит разматывание стека:

```text
CancelledError
→ except внутри use_resource логирует и делает raise
→ finally закрывает ресурс
→ управление выходит из use_resource
→ timeout-контекст перехватывает свою отмену
→ преобразует её в TimeoutError
→ main ловит TimeoutError
```

Поэтому:

- `use_resource()` видит `CancelledError`;
- `main()` снаружи timeout-контекста видит `TimeoutError`.

### 3. Почему `finally` выполнился первым

Это не случайность и не вопрос того, «успел» ли блок по времени. Когда исключение выходит из `try`, Python обязан выполнить соответствующий `finally` во время разматывания стека.

Только после cleanup управление окончательно выходит из coroutine и timeout-контекста. Поэтому внешний `except TimeoutError` срабатывает позже.

### 4. Почему программа продолжилась

`main()` поймала `TimeoutError`:

```python
except TimeoutError:
    print("main: получен TimeoutError")
```

Исключение обработано, поэтому Python переходит к следующей строке:

```python
print("main: программа продолжилась")
```

### 5. Риск незакрытого соединения БД

Основной риск — не «утечка данных», а утечка ресурса:

- соединение не возвращается в pool;
- pool постепенно исчерпывается;
- новые запросы ждут свободное соединение;
- незавершённая транзакция может удерживать locks;
- приложение начинает получать timeout и ошибки подключения.
