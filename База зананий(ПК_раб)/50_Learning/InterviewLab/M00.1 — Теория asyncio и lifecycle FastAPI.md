# M00.1 — Теория: asyncio и lifecycle FastAPI

## Зачем backend-разработчику эта тема

FastAPI работает поверх ASGI — интерфейса между Python web-приложением и сервером. ASGI позволяет одному процессу эффективно обслуживать множество запросов, пока часть из них ожидает сеть, базу данных, Redis или другой внешний сервис.

Асинхронность не делает отдельную операцию быстрее. Она позволяет полезно занять время, которое иначе процесс потратил бы на ожидание.

Чтобы безопасно писать async backend, нужно понимать:

- что именно создаёт `async def`;
- что происходит при `await`;
- как event loop переключает задачи;
- почему синхронный I/O блокирует приложение;
- чем coroutine отличается от Task;
- как работают timeout и cancellation;
- какие ресурсы должны создаваться и закрываться через lifespan FastAPI.

---

## 1. Базовые термины

### Синхронное выполнение

Синхронный код выполняет действия последовательно. Пока текущая функция не завершилась, вызывающий код не продолжает работу.

```python
result = load_from_network()
print(result)
```

Если `load_from_network()` ждёт ответ две секунды, текущий поток две секунды не может продолжить этот участок программы.

### Асинхронное выполнение

Асинхронный код способен приостановить текущую операцию в точке ожидания и дать event loop возможность выполнять другие готовые операции.

Важно: асинхронность — это не автоматическое создание потоков и не параллельное исполнение Python-кода.

### I/O-bound задача

Задача большую часть времени ждёт ввод-вывод:

- HTTP-ответ;
- PostgreSQL;
- Redis;
- RabbitMQ;
- чтение из сокета;
- иногда диск.

Для таких задач async обычно полезен.

### CPU-bound задача

Задача большую часть времени выполняет вычисления:

- обработка изображения;
- сжатие большого массива данных;
- сложный расчёт;
- локальный ML inference;
- преобразование большого документа.

Обычный `asyncio` не ускоряет CPU-bound код. Пока такой код выполняется в потоке event loop, другие задачи не получают управление.

### Конкурентность

Несколько задач находятся в работе одновременно по времени, но процесс может переключаться между ними. Пока одна ожидает сеть, выполняется другая.

### Параллелизм

Несколько операций физически выполняются одновременно, например на разных ядрах CPU или в разных процессах.

Asyncio прежде всего даёт конкурентность. Для CPU-параллелизма обычно применяют процессы, отдельные workers или вычисления в native-коде.

## 2. Coroutine function и coroutine object

Функция, объявленная через `async def`, называется coroutine function:

```python
async def load_user() -> dict[str, str]:
    return {"name": "Pavel"}
```

Вызов такой функции не выполняет её тело до конца и не создаёт отдельный поток:

```python
coroutine = load_user()
```

В переменной `coroutine` находится coroutine object — описание приостанавливаемого вычисления.

Чтобы вычисление действительно выполнилось, coroutine нужно:

- ожидать через `await`;
- запланировать как Task;
- передать в механизм, который сам создаст и дождётся Task.

Если создать coroutine object и никогда его не ожидать, Python обычно предупредит: `coroutine was never awaited`.

### Простая мысленная модель

Coroutine object похож не на готовый результат, а на оформленную заявку на работу. Заявка описывает, что нужно сделать, но ещё не означает, что работа поставлена в расписание.

## 3. Event loop

Event loop — диспетчер асинхронного приложения. Он:

- хранит запланированные задачи;
- запускает готовые участки coroutine;
- следит за сетевыми событиями;
- возобновляет задачу, когда ожидаемый результат готов;
- запускает callbacks и таймеры.

В типичном FastAPI worker один event loop работает в одном потоке.

Event loop использует кооперативное переключение. Это значит, что задача сама должна дойти до точки, где она отдаёт управление — обычно до `await` операции, которая ещё не завершена.

Если задача долго выполняет обычный Python-код без `await`, event loop не может принудительно остановить её и запустить соседнюю задачу.

### Упрощённая временная линия

```text
Task A: отправила HTTP-запрос ───── ждёт ───── получила ответ ── продолжила
Task B:                         запрос в DB ─ ждёт ─ результат ─ продолжила
Task C:                                      обработала готовые данные
```

Один поток не выполняет три участка Python одновременно. Он выполняет готовый участок одной задачи, а в периоды ожидания переключается на другую.

---

## 4. Что происходит на `await`

Рассмотрим:

```python
result = await load_user()
```

Упрощённо происходят следующие шаги:

1. Создаётся coroutine object `load_user()`.
2. Текущая Task начинает выполнять эту coroutine.
3. Если `load_user()` может сразу продолжать работу, она продолжает выполняться.
4. Если внутри встречается незавершённая асинхронная I/O-операция, текущая Task приостанавливается.
5. Управление возвращается event loop.
6. Event loop запускает другую готовую Task.
7. Когда I/O готово, исходная Task снова становится готовой.
8. Event loop возобновляет её, а `await` в итоге возвращает результат или выбрасывает исключение.

Ключевые свойства:

- `await` не создаёт новый thread;
- `await` не обязательно создаёт отдельную Task;
- вызывающая Task логически ждёт результат;
- другие Task могут выполняться только если event loop получил управление;
- `await` обычной CPU-функции невозможен и не сделал бы её неблокирующей.

### Последовательное ожидание

```python
first = await load_first()
second = await load_second()
```

Вторая операция начнётся только после завершения первой.

Это асинхронный код, но две операции выполняются последовательно.

## 5. Task

Task — coroutine, зарегистрированная в event loop для конкурентного выполнения.

```python
task = asyncio.create_task(load_user())
```

После `create_task` event loop получает возможность начать выполнение `load_user`, когда текущая Task отдаст управление.

Позже результат можно получить:

```python
user = await task
```

Разница:

```python
result = await load_user()
```

Текущая Task сразу переходит к выполнению `load_user` и ждёт результат.

```python
task = asyncio.create_task(load_user())
```

Создаётся отдельная Task. Текущий код может выполнить другие действия до `await task`.

### Конкурентный запуск

```python
async with asyncio.TaskGroup() as group:
    user_task = group.create_task(load_user())
    orders_task = group.create_task(load_orders())

user = user_task.result()
orders = orders_task.result()
```

Обе операции могут ожидать I/O конкурентно. Выход из `TaskGroup` гарантирует, что все дочерние задачи завершились. Если одна завершится ошибкой, группа отменит остальные и соберёт ошибки предсказуемым способом.

Этот подход называют structured concurrency: жизненный цикл дочерних задач ограничен видимым блоком программы.

### `gather` и `TaskGroup`

`asyncio.gather()` удобно собирает результаты нескольких awaitable в заданном порядке:

```python
user, orders = await asyncio.gather(
    load_user(),
    load_orders(),
)
```

`TaskGroup` обычно даёт более строгие гарантии при ошибке одной из связанных задач: остальные задачи группы отменяются, и выполнение не оставляет незавершённую работу вне блока.

## 6. Почему `requests` блокирует async endpoint

Проблемный пример:

```python
@app.get("/external-data")
async def external_data() -> dict:
    response = requests.get("https://example.com/data")
    return response.json()
```

Функция `requests.get()` синхронная. Она не сообщает event loop: «я ожидаю сеть, можешь выполнить другую Task». Поток просто блокируется внутри библиотеки.

Пока внешний сервер отвечает:

- текущий endpoint стоит;
- event loop в этом потоке тоже стоит;
- другие async endpoints того же worker могут задерживаться;
- растёт latency;
- под нагрузкой падает пропускная способность.

Наличие `async def` вокруг синхронного вызова ничего не исправляет.

### Основное решение: async HTTP client

```python
async with httpx.AsyncClient(timeout=5.0) as client:
    response = await client.get("https://example.com/data")
    response.raise_for_status()
    data = response.json()
```

Но создавать новый клиент на каждый запрос не всегда выгодно: теряется переиспользование соединений. В приложении обычно создают один клиент на lifespan процесса и корректно закрывают при shutdown.

### Временная адаптация синхронной библиотеки

```python
result = await asyncio.to_thread(sync_function)
```

Синхронная функция выполняется в thread pool, поэтому event loop не блокируется. Это полезно, когда async-аналога нет.

Ограничения:

- число threads ограничено;
- синхронная библиотека должна быть thread-safe в используемом режиме;
- это не хороший способ ускорять тяжёлый Python CPU-код из-за GIL;
- timeout и отмена внешней операции могут работать не так прозрачно, как у native async API.

## 7. GIL, threads и processes

GIL — механизм CPython, который в обычной сборке не позволяет нескольким threads одновременно исполнять Python bytecode внутри одного процесса.

Это не означает, что threads бесполезны:

- во время блокирующего I/O поток может освободить GIL;
- несколько I/O-операций могут эффективно перекрываться;
- многие native-библиотеки освобождают GIL во время вычислений.

Практическая карта выбора:

| Работа | Обычно выбирать |
|---|---|
| Много сетевого async I/O | asyncio |
| Есть только синхронная I/O-библиотека | thread pool / `to_thread` |
| Тяжёлый Python CPU-код | process pool или отдельный worker |
| Надёжная долгая фоновая задача | RabbitMQ + worker |
| Короткая связанная конкурентная работа | `TaskGroup` |

`asyncio.create_task()` нельзя считать заменой RabbitMQ. Task существует только в памяти процесса. При падении или перезапуске процесса работа теряется.

## 8. Timeout

Любой сетевой вызов может зависнуть или отвечать слишком долго. Поэтому внешний I/O должен иметь ограничение времени.

```python
try:
    async with asyncio.timeout(3):
        result = await slow_operation()
except TimeoutError:
    result = None
```

Когда лимит истекает, asyncio инициирует отмену текущей операции. Контекст `asyncio.timeout()` преобразует внутреннюю отмену в `TimeoutError`, который обрабатывается снаружи блока.

Timeout — не retry. Он только ограничивает время одной попытки или блока операций.

Retry также должен быть ограничен:

- максимальным числом попыток;
- общим временным бюджетом;
- backoff;
- типами ошибок;
- идемпотентностью операции.

Повторять платёж без idempotency key опасно.

## 9. Cancellation

Cancellation — запрос на отмену Task.

```python
task.cancel()
```

На ближайшей подходящей точке выполнения в Task возникает `asyncio.CancelledError`.

Coroutine должна освобождать ресурсы через `finally`:

```python
async def worker() -> None:
    resource = await acquire_resource()
    try:
        await perform_work(resource)
    finally:
        await release_resource(resource)
```

Обычно `CancelledError` не следует молча подавлять. После cleanup отмена должна распространиться выше. Иначе могут неправильно работать `TaskGroup`, timeout и graceful shutdown.

Cancellation особенно важна, когда:

- клиент разорвал HTTP-соединение;
- сработал timeout;
- приложение останавливается;
- одна задача внутри `TaskGroup` завершилась ошибкой.

## 10. Lifespan FastAPI

Lifespan — период жизни процесса приложения:

```text
startup → обработка множества запросов → shutdown
```

Ресурсы, которые нужны многим запросам, часто создаются один раз при startup и закрываются при shutdown:

- HTTP connection pool;
- database engine/pool;
- Redis client;
- RabbitMQ connection;
- загруженная модель;
- background supervisor с контролируемым завершением.

Пример:

```python
from collections.abc import AsyncIterator
from contextlib import asynccontextmanager

import httpx
from fastapi import FastAPI, Request


@asynccontextmanager
async def lifespan(app: FastAPI) -> AsyncIterator[None]:
    app.state.http_client = httpx.AsyncClient(timeout=5.0)
    try:
        yield
    finally:
        await app.state.http_client.aclose()


app = FastAPI(lifespan=lifespan)


@app.get("/external")
async def external(request: Request) -> dict:
    client: httpx.AsyncClient = request.app.state.http_client
    response = await client.get("https://example.com/data")
    response.raise_for_status()
    return response.json()
```

Код до `yield` выполняется перед приёмом запросов. Код после `yield` выполняется при остановке и освобождает ресурсы.

FastAPI рекомендует lifespan вместо старых раздельных обработчиков `startup` и `shutdown`.

### Почему не создавать клиент при импорте модуля

Объект, созданный на уровне модуля:

- возникает ещё при импорте;
- усложняет тестирование;
- может быть привязан к неправильному event loop;
- не имеет очевидного места корректного закрытия;
- затрудняет замену зависимости.

Lifespan делает момент создания и cleanup явным.

## 11. Как это связано с FastAPI endpoint

### `async def` endpoint

Используется, когда вызываемые библиотеки имеют async API:

```python
@app.get("/users/{user_id}")
async def get_user(user_id: int) -> UserResponse:
    user = await repository.get(user_id)
    return UserResponse.model_validate(user)
```

### Обычный `def` endpoint

FastAPI выполняет обычные path operation functions во внешнем thread pool, чтобы они не блокировали event loop напрямую. Это может быть разумно при работе с синхронной библиотекой.

Но thread pool не бесконечен. Если множество запросов надолго занимают его threads, приложение всё равно упрётся в ограничение ресурсов.

Главное правило: выбирайте стиль endpoint по модели используемых библиотек, а не потому, что `async` выглядит современнее.

## 12. Частые ошибки

### Ошибка 1. Считать `async def` автоматическим ускорением

Без неблокирующих операций async не даёт преимущества.

### Ошибка 2. Вызывать `requests`, синхронный драйвер БД или `time.sleep` внутри async endpoint

Они блокируют поток event loop. Для задержки в async-коде используется `await asyncio.sleep(...)`.

### Ошибка 3. Последовательно ожидать независимые операции

Если операции независимы, стоит рассмотреть `TaskGroup` или `gather`. Если вторая зависит от результата первой, конкурентный запуск невозможен.

### Ошибка 4. Создавать fire-and-forget Task для обязательной работы

Задача может потеряться при shutdown или падении процесса. Обязательная работа должна иметь внешний durable storage — например RabbitMQ.

### Ошибка 5. Не задавать timeout

Одна зависшая интеграция постепенно занимает все доступные ресурсы.

### Ошибка 6. Подавлять `CancelledError`

Это нарушает нормальное завершение приложения и structured concurrency.

### Ошибка 7. Создавать новый HTTP client на каждый вызов

Так теряются преимущества connection pooling и keep-alive.

### Ошибка 8. Запускать тяжёлое CPU-вычисление в event loop

Другие запросы перестают обслуживаться, пока вычисление не завершится.

## 13. Метод принятия решения

Для любой операции задайте пять вопросов:

1. Это I/O-bound или CPU-bound работа?
2. Библиотека синхронная или асинхронная?
3. Должна ли операция пережить перезапуск процесса?
4. Какой допустим timeout?
5. Что произойдёт при отмене или частичном выполнении?

Примеры:

| Операция | Решение |
|---|---|
| Запрос к PostgreSQL через asyncpg | `await` async-драйвера |
| Запрос к OpenRouter через httpx | shared `AsyncClient` + timeout |
| Старая синхронная SDK интеграции | временно `to_thread` или sync endpoint |
| Отправка обязательного email | RabbitMQ + worker |
| Два независимых HTTP-запроса | `TaskGroup` |
| Генерация большого PDF | отдельный process/worker |

## 14. Краткая схема для запоминания

```text
async def   → объявляет coroutine function
вызов       → создаёт coroutine object
await       → выполняет/ожидает, не создавая thread
Task        → coroutine, запланированная в event loop
event loop  → выполняет готовые участки Task и следит за I/O
blocking I/O→ не отдаёт управление event loop
timeout     → ограничивает ожидание через cancellation
lifespan    → создаёт и закрывает общие ресурсы приложения
RabbitMQ    → хранит обязательную работу вне процесса FastAPI
```
