# M00.3 — Микроурок 1: Coroutine, Task и Event Loop

Предварительный фундамент: [[M00.0 — Как Python исполняет Flask приложение]].

## Мост от Flask к asyncio

### Термины совсем простыми словами

Представим небольшой офис, который принимает заявления посетителей.

```text
Офис                   → process
Сотрудник за столом    → thread
Сотрудник на работе    → worker thread
Группа сотрудников     → thread pool
Стопка заявлений       → request queue
Одно заявление         → HTTP request
Правила работы офиса   → Flask-приложение
Администратор при входе→ Waitress
```

Теперь разберём каждое слово отдельно.

#### Process — отдельный офис

Process — запущенная программа со своей памятью.

Когда Windows запускает Python-сервер, появляется отдельный «офис»:

- у него есть номер — PID;
- своё помещение — область памяти;
- свои предметы — Python-объекты;
- свои сотрудники — threads;
- свой экземпляр CPython и GIL.

Другой process похож на второй отдельный офис. У него свои столы и свои копии документов. Изменение листка в первом офисе не изменит листок во втором.

#### Thread — сотрудник, который выполняет инструкции

Thread — последовательность выполнения команд внутри process.

Можно представить thread как одного сотрудника, который читает инструкцию строка за строкой:

```text
получи запрос
найди маршрут
вызови функцию
получи данные из БД
сформируй ответ
```

У каждого сотрудника есть собственная текущая работа — свой call stack. Но сотрудники одного офиса могут пользоваться общими шкафами, то есть общей памятью process.

#### Worker — исполнитель работы

Worker буквально означает «работник» или «исполнитель».

Это роль, а не специальный тип данных Python. Worker — тот, кому система выдаёт работу.

В разных системах worker может быть разным:

- в Waitress — thread;
- в Gunicorn — часто process;
- в Celery — process или thread, который получает задачи из очереди;
- в Uvicorn — server process с event loop.

Поэтому всегда уточняйте: worker какого типа?

#### Worker thread — поток, которому сервер выдаёт запросы

Worker thread — обычный thread, назначенный выполнять работу из очереди.

Waitress держит несколько таких threads. Когда приходит готовый HTTP-запрос, Waitress отдаёт его свободному worker thread.

```text
Запрос A → worker thread 1
Запрос B → worker thread 2
Запрос C → worker thread 3
```

Worker thread выполняет Flask-код запроса до получения response. После этого он снова свободен и может взять следующий запрос.

Важно: сервер обычно не создаёт новый thread специально для каждого запроса. Он заранее держит ограниченную группу переиспользуемых threads.

#### Thread pool — команда сотрудников

Pool означает «набор» или «группа» заранее подготовленных ресурсов.

Thread pool — ограниченная группа threads, готовых получать работу:

```text
Thread pool Waitress
├─ worker thread 1 — занят запросом A
├─ worker thread 2 — свободен
├─ worker thread 3 — занят запросом B
└─ worker thread 4 — свободен
```

Почему pool ограничен:

- каждый thread потребляет память;
- операционная система тратит время на переключения;
- слишком много одновременной работы перегружает БД и внешние сервисы;
- бесконечное создание threads не устраняет медленный код.

#### Request queue — очередь заявлений

Queue — очередь ожидающих работ.

Если пришло пять запросов, а все четыре worker threads заняты, пятый запрос ожидает:

```text
Threads: [занят] [занят] [занят] [занят]
Queue:   [запрос 5] [запрос 6]
```

Когда один thread завершает работу, он берёт следующий запрос из очереди.

Ожидание в очереди не бесконечно безопасно. Клиент, reverse proxy или load balancer может прекратить ожидание по timeout.

#### Что значит «thread занят»

Thread занят от начала обработки WSGI-запроса до возврата response.

Если функция выполняет:

```python
data = database.execute(query)
```

и база отвечает пять секунд, этот worker thread пять секунд не может взять другой Flask-запрос. Он ожидает, оставаясь закреплённым за текущим запросом.

Другие свободные threads при этом могут продолжать работать.

#### Как threads используют общую память

В одном process сотрудники работают в одном офисе и видят общий шкаф:

```python
shared_cache = {}
```

Два worker threads могут одновременно читать и изменять `shared_cache`. Поэтому возможны гонки и потерянные обновления.

У каждого thread свой путь выполнения, но Python-объекты в heap процесса общие.

#### Чем worker thread не является

Worker thread — это не:

- отдельное Flask-приложение;
- отдельный process;
- отдельная копия всей памяти;
- coroutine;
- async Task;
- задача RabbitMQ.

Это поток выполнения ОС внутри process, который сервер использует как исполнителя запросов.

### Та же схема без аналогии

```text
Windows запускает Python process
    ↓
в process работает Waitress
    ↓
Waitress содержит thread pool
    ↓
HTTP request попадает в очередь
    ↓
свободный worker thread вызывает app.wsgi_app
    ↓
Flask выполняет view function
    ↓
response возвращается Waitress
    ↓
worker thread освобождается
```

### Где заканчивается аналогия

Аналогия с офисом помогает увидеть роли, но технически:

- thread не является человеком — это объект планирования операционной системы;
- Waitress может отдельно управлять сетевым I/O и выполнением WSGI-задач;
- GIL ограничивает одновременное исполнение Python bytecode threads одного обычного CPython process;
- операционная система сама планирует, когда конкретный thread получает время CPU.

### Мини-проверка терминов

Заполните после чтения одним словом или короткой фразой:

1. Запущенная программа со своей памятью — это ...
2. Исполнитель команд внутри process — это ...
3. Ограниченная группа threads — это ...
4. Thread, которому Waitress выдаёт HTTP-запрос, — это ...
5. Место, где запрос ждёт свободного исполнителя, — это ...

Ответы:

1.Process
2. Worker thread
3. Pool threads - это готовые потоки которые ожидают выполнение работы (кода)
4.Worker (исполнитель работы)
5.Request queue

В разобранной модели Flask/Waitress четыре одновременных синхронных запроса могли занимать четыре worker threads:

```text
один process
├─ worker thread 1 → request A
├─ worker thread 2 → request B
├─ worker thread 3 → request C
└─ worker thread 4 → request D
```

В базовой async-модели один thread содержит event loop, а запросы представлены Task:

```text
один process
└─ один thread с event loop
   ├─ Task A → выполняется или ожидает I/O
   ├─ Task B → выполняется или ожидает I/O
   ├─ Task C → выполняется или ожидает I/O
   └─ Task D → выполняется или ожидает I/O
```

Thread — сущность операционной системы со своим стеком. Task — Python-объект внутри event loop. Task не является thread. Event loop выполняет в своём thread готовые участки Task по очереди; переключение происходит кооперативно, когда текущая Task доходит до незавершённого `await`.

## Важное уточнение: запрос пользователя не «всегда синхронный»

Здесь легко смешать три разных уровня:

1. HTTP как обмен сообщениями;
2. поведение клиента, например браузера;
3. модель выполнения Python-сервера.

### Уровень 1. HTTP-запрос

Клиент отправляет серверу сообщение:

```text
GET /health HTTP/1.1
Host: example.com
```

Сервер позже отправляет HTTP-response. Само сообщение не является Python coroutine, thread или Task. Это байты, передаваемые через сетевое соединение.

HTTP часто использует модель request → response, но из этого не следует, что сервер обязан обрабатывать запрос синхронно.

### Уровень 2. Что делает клиент

Клиент может ждать ответ по-разному.

Синхронный Python-клиент:

```python
response = requests.get(url)
print(response.json())
```

Текущий thread клиента заблокирован до получения ответа или ошибки.

Асинхронный Python-клиент:

```python
response = await httpx_client.get(url)
print(response.json())
```

Текущая Task клиента приостанавливается. Event loop может выполнять другие Task.

В браузере JavaScript-запрос через `fetch` тоже асинхронен относительно интерфейса страницы:

```javascript
const response = await fetch("/health");
```

Пока сеть отвечает, браузер способен продолжать обслуживать интерфейс и другие события.

### Уровень 3. Что делает Python-сервер

Один и тот же `GET /health` можно обработать разными способами.

#### Flask + Waitress

```text
запрос → worker thread → синхронная view → response
```

Пока view ждёт синхронную БД, worker thread занят. Другие запросы обслуживают другие свободные threads.

#### FastAPI + Uvicorn

```text
запрос → async Task в event loop → async endpoint → response
```

Пока endpoint ожидает async БД через `await`, Task приостановлена, а тот же event-loop thread может выполнять другие Task.

Следовательно, один и тот же HTTP-запрос не определяет модель выполнения. Её определяют сервер, framework, вид endpoint и используемые библиотеки.

## Почему не нужно применять `asyncio` всегда

`asyncio` полезно, когда одновременно выполняется много I/O-bound операций:

- запросы к PostgreSQL через async-драйвер;
- обращения к Redis;
- HTTP-запросы во внешние API;
- WebSocket-соединения;
- ожидание сообщений или сетевых событий.

Но `asyncio` не обязательно и не всегда подходит.

### Случай 1. Синхронный Flask работает нормально

Если приложение:

- имеет небольшую нагрузку;
- использует синхронные библиотеки;
- имеет достаточно worker threads;
- задаёт timeout внешним операциям;
- не держит множество долгих соединений;

то Flask + Waitress может быть корректным production-решением.

### Случай 2. CPU-bound код

```python
@app.get("/calculate")
async def calculate():
    result = very_heavy_python_calculation()
    return {"result": result}
```

Здесь `async def` не помогает. Тяжёлое вычисление не доходит до `await` и блокирует event-loop thread. Для такой работы обычно нужен отдельный process или worker.

### Случай 3. Внутри async endpoint вызвана sync-библиотека

```python
@app.get("/external")
async def external():
    return requests.get(url).json()
```

`requests.get()` не умеет сообщить event loop об ожидании. Поэтому блокируется event-loop thread, а вместе с ним задерживаются другие Task.

Решения:

- использовать async-клиент, например `httpx.AsyncClient`;
- временно вынести sync I/O в thread pool;
- сделать endpoint обычным `def`, если весь его стек синхронный;
- вынести долгую обязательную работу в очередь.

## Где здесь находится библиотека `asyncio`

`asyncio` — стандартная библиотека Python для управления:

- event loop;
- coroutine;
- Task;
- ожиданием I/O;
- timeout;
- cancellation;
- примитивами синхронизации async-кода.

FastAPI не требует, чтобы в каждом endpoint вы вручную писали `asyncio.run()`. Event loop уже запускает ASGI-server, например Uvicorn.

Внутри endpoint обычно используются `async def` и `await`:

```python
@app.get("/users/{user_id}")
async def get_user(user_id: int):
    user = await repository.get(user_id)
    return user
```

Низкоуровневое управление через `asyncio` требуется, например, когда нужно:

- конкурентно запустить независимые операции через `TaskGroup`;
- задать общий timeout;
- управлять cancellation;
- ограничить конкурентность через `Semaphore`.

|---|---|

Фраза для запоминания:

> Не пользовательский запрос заставляет применять asyncio. Asyncio выбирают, когда модель сервера и характер I/O позволяют одному event loop эффективно переключать множество ожидающих Task.

## Цель

После урока нужно понимать не определения по отдельности, а путь работы:

```text
async-функция → coroutine object → Task → выполнение event loop
```

В этом уроке нет FastAPI, HTTP, RabbitMQ, timeout и cancellation. Сначала строим фундамент.

---

## 1. Обычная функция

```python
def make_message() -> str:
    print("Функция начала работу")
    return "готово"


result = make_message()
```

При вызове `make_message()` Python сразу входит в тело функции:

1. выполняет `print`;
2. создаёт строку;
3. возвращает результат;
4. записывает результат в `result`.

Здесь вызов функции означает начало её выполнения.

---

## 2. Async-функция

```python
async def make_message() -> str:
    print("Coroutine начала работу")
    return "готово"


coroutine = make_message()
```

При строке `make_message()` тело ещё не выполняется. Надпись не печатается.

Python создаёт coroutine object. Это объект, который хранит:

- какой код нужно выполнить;
- его локальное состояние;
- место, с которого выполнение можно будет продолжить после остановки.

Coroutine object — ещё не запланированная работа.

### Аналогия

`async def` — рецепт.

Вызов `make_message()` — карточка заказа по этому рецепту.

Coroutine object — заполненная карточка заказа, которая ещё не передана повару.

---

## 3. Что делает `await`

```python
result = await make_message()
```

`await` говорит текущей Task: «выполни эту coroutine и не продолжай следующий шаг, пока не получишь результат».

Если внутри coroutine встречается ожидание незавершённого I/O, текущая Task временно останавливается и возвращает управление event loop.

Важно различать:

- останавливается не весь процесс;
- останавливается текущая Task;
- event loop может запустить другую готовую Task;
- новый thread не создаётся.

Если внутри coroutine нет реального ожидания, она может завершиться сразу, не отдавая управление другим задачам.

---

## 4. Что делает Task

```python
task = asyncio.create_task(make_message())
```

`create_task`:

1. принимает coroutine object;
2. оборачивает его в Task;
3. регистрирует Task в текущем event loop;
4. возвращает управление вызывающему коду.

Task означает: «эта coroutine теперь включена в расписание event loop».

Она начнёт исполняться, когда текущий код отдаст управление event loop, например дойдёт до `await`.

`create_task` не означает:

- новый процесс;
- новый thread;
- немедленное параллельное выполнение;
- надёжное хранение задачи после остановки приложения.

---

## 5. Что делает Event Loop

Event loop можно представить как диспетчера одного рабочего стола.

Он по очереди даёт стол готовым Task:

```mermaid
sequenceDiagram
    participant Main as "Task main"
    participant Loop as "Event loop"
    participant Work as "Task work"

    Main->>Loop: "create_task(work())"
    Note over Main: "main продолжает текущий участок"
    Main->>Loop: "await sleep(...) — отдаёт управление"
    Loop->>Work: "можно выполнять"
    Work->>Loop: "await I/O — временно останавливаюсь"
    Loop->>Main: "возобновляю готовую main"
    Loop->>Work: "I/O готово — продолжай"
```

Event loop выполняет только готовую работу. Если Task ожидает сеть, она временно не готова. Если Task выполняет длинный обычный Python-код, она не отдаёт рабочий стол остальным.

---

## 6. Главное различие

| Конструкция | Что появляется | Началось ли выполнение тела? |
|---|---|---|
| `make_message()` | Coroutine object | Нет |
| `await make_message()` | Выполнение coroutine внутри текущей Task | Да |
| `create_task(make_message())` | Отдельная Task в расписании loop | Начнётся при передаче управления loop |
| `await task` | Ожидание результата созданной Task | Task уже могла выполняться |

Фраза для запоминания:

> Coroutine описывает приостанавливаемую работу. Task ставит эту работу в расписание. Event loop выполняет готовые Task. Await связывает текущую Task с ожидаемым результатом и при необходимости отдаёт управление loop.

### Одно наблюдение после запуска

В какой строке `main()` впервые отдала управление event loop и какая Task после этого начала выполняться?

Ответ ученика:

> Корутина без await или create_task — просто «бумажка», она не исполняется.
>
> Task — это «бумажка, переданная официанту»; она начинает выполняться, только когда официант (event loop) получает возможность переключиться после await.

Техническое уточнение: `main()` впервые отдаёт управление на `await asyncio.sleep(0)`. После этого event loop запускает Task, созданную из `work("task")`.

## 8. Мини-проверка урока

Закончите три предложения своими словами:

1. Вызов async-функции сам по себе не запускает тело, потому что это контракт
2. Task отличается от coroutine object тем, что ею можно управлять  в event loop
3. Event loop может переключиться на другую Task, когда при запросе к БД

После этого микроурок 1 считается пройденным. Следующий микроурок будет посвящён только `await`: последовательному и конкурентному выполнению.

## Разбор преподавателя — 2026-08-17

### Термины

- `Process` — верно.
- Во втором ответе точнее `thread`: не каждый thread обязательно является worker. Worker — роль исполнителя.
- `Thread pool` — смысл понят верно: ограниченная группа переиспользуемых threads.
- В четвёртом ответе точнее `worker thread`, потому что вопрос спрашивает именно thread, которому Waitress выдаёт запрос.
- `Request queue` — верно.

### Итоговые фразы

Точная модель:

1. Вызов async-функции создаёт coroutine object, но не ставит его в расписание event loop.
2. Task — coroutine, обёрнутая в объект, который зарегистрирован в event loop и имеет состояние выполнения, результат, исключение и возможность отмены.
3. Event loop может выполнить другую Task, когда текущая Task дошла до незавершённого `await` и кооперативно отдала управление.
