# M00.7 — Lifespan FastAPI и владение ресурсами

## Цель

Понять жизненный цикл FastAPI-приложения и ответить на вопрос:

> Кто создаёт общий ресурс, кто им пользуется и кто обязан его закрыть?

## 1. Аналогия с офисом

Приложение похоже на офис:

```text
Открытие офиса             → startup
Офис работает весь день   → обработка запросов
Закрытие офиса             → shutdown
```

Перед открытием:

- включают серверы;
- открывают общие шкафы;
- создают оборудование;
- проверяют готовность.

После закрытия:

- возвращают ключи;
- закрывают соединения;
- сохраняют состояние;
- освобождают ресурсы.

В FastAPI эту границу описывает lifespan.

## 2. Что такое lifespan

Lifespan — жизненный цикл одного экземпляра приложения внутри одного server process:

```text
код до yield
    ↓
startup завершён
    ↓
приложение принимает много запросов
    ↓
начинается shutdown
    ↓
код после yield
```

Пример:

```python
from collections.abc import AsyncIterator
from contextlib import asynccontextmanager

from fastapi import FastAPI


@asynccontextmanager
async def lifespan(app: FastAPI) -> AsyncIterator[None]:
    print("startup: создаём ресурсы")
    app.state.resource = object()

    try:
        yield
    finally:
        print("shutdown: закрываем ресурсы")


app = FastAPI(lifespan=lifespan)
```

До `yield` выполняется startup. После `yield` — shutdown и cleanup.

## 3. Lifespan выполняется не для каждого запроса

Предположим, приложение обработало тысячу запросов:

```text
startup — 1 раз
request — 1000 раз
shutdown — 1 раз
```

Это позволяет переиспользовать дорогие ресурсы.

## 4. Каждый worker process имеет свой lifespan

Если Uvicorn запущен с четырьмя worker processes:

```text
Process 1 → свой app → свой lifespan → свой HTTP client
Process 2 → свой app → свой lifespan → свой HTTP client
Process 3 → свой app → свой lifespan → свой HTTP client
Process 4 → свой app → свой lifespan → свой HTTP client
```

Память процессов раздельна. Один общий Python-объект нельзя разделить между ними обычной глобальной переменной.

Поэтому четыре processes могут создать четыре отдельных connection pools. Это нужно учитывать при расчёте лимита соединений PostgreSQL и внешних сервисов.

## 5. Какие ресурсы живут на каком уровне

### Application-scoped — весь lifespan process

Обычно создаются один раз на экземпляр приложения:

- `httpx.AsyncClient`;
- SQLAlchemy `AsyncEngine` и connection pool;
- Redis client/pool;
- RabbitMQ connection/channel manager;
- загруженная ML-модель;
- registry метрик.

### Request-scoped — один HTTP-запрос

Обычно создаются для запроса и закрываются после него:

- SQLAlchemy `AsyncSession`;
- транзакция запроса;
- текущий пользователь;
- correlation/request ID;
- unit of work.

### Operation-scoped — одна операция

- временный файл;
- lock;
- stream;
- savepoint;
- timeout-блок.

Главное правило:

> Владелец ресурса должен иметь понятное место cleanup на том же уровне жизненного цикла.

## 6. Почему HTTP client переиспользуют

Проблемный вариант:

```python
@app.get("/external")
async def external():
    async with httpx.AsyncClient() as client:
        response = await client.get(url)
        return response.json()
```

Для каждого запроса создаётся и закрывается новый client. Это мешает эффективно использовать:

- connection pool;
- keep-alive;
- повторное TCP-соединение;
- повторное TLS-соединение;
- централизованные timeout и headers.

Application-scoped client:

```python
@asynccontextmanager
async def lifespan(app: FastAPI) -> AsyncIterator[None]:
    app.state.http_client = httpx.AsyncClient(timeout=5.0)
    try:
        yield
    finally:
        await app.state.http_client.aclose()
```

Теперь много endpoint используют один pool соединений текущего process.

## 7. Почему не создавать async client при импорте

Проблемный вариант:

```python
client = httpx.AsyncClient()
```

на верхнем уровне модуля.

Риски:

- объект создаётся при любом импорте, включая тесты и команды миграций;
- момент startup скрыт;
- место закрытия неочевидно;
- ресурс может создаться до корректной настройки event loop;
- трудно подменять конфигурацию и зависимости;
- несколько импортирующих сценариев становятся сложнее анализировать.

Lifespan делает владение явным:

```text
lifespan создал → приложение использует → lifespan закрыл
```

## 8. `app.state` и dependency injection

Endpoint не обязан напрямую знать детали создания клиента. Dependency может получить application-scoped ресурс:

```python
from typing import Annotated

import httpx
from fastapi import Depends, Request


def get_http_client(request: Request) -> httpx.AsyncClient:
    return request.app.state.http_client


HttpClient = Annotated[httpx.AsyncClient, Depends(get_http_client)]


@app.get("/external")
async def external(client: HttpClient):
    response = await client.get("https://example.com")
    return response.json()
```

Lifespan владеет клиентом. Dependency только предоставляет ссылку endpoint.

## 9. Request-scoped dependency с `yield`

Для сессии БД жизненный цикл другой:

```python
async def get_session() -> AsyncIterator[AsyncSession]:
    async with session_factory() as session:
        yield session
```

На каждый запрос:

```text
создать AsyncSession
↓
передать endpoint/service
↓
завершить запрос
↓
закрыть AsyncSession
```

Не следует хранить один `AsyncSession` на всё приложение. Сессия содержит состояние unit of work и не предназначена для одновременного использования несколькими запросами.

Различие:

```text
AsyncEngine/pool → lifespan приложения
AsyncSession     → один запрос/unit of work
```

## 10. Shutdown и cancellation

При остановке server:

1. прекращается приём новой работы;
2. текущим операциям дают время завершиться;
3. оставшиеся Task могут отменяться;
4. lifespan выходит из `yield`;
5. выполняется cleanup.

Именно поэтому cleanup помещают в `finally`. Даже если shutdown связан с исключением или cancellation, ресурсы должны освобождаться.

## 11. Практическое наблюдение

Создайте файл `lifespan_observation.py` в активированном окружении с FastAPI:

```python
from collections.abc import AsyncIterator
from contextlib import asynccontextmanager

from fastapi import FastAPI, Request
from fastapi.testclient import TestClient


class Resource:
    def __init__(self) -> None:
        print("resource: создан")

    def use(self) -> str:
        print("resource: использован")
        return "ok"

    def close(self) -> None:
        print("resource: закрыт")


@asynccontextmanager
async def lifespan(app: FastAPI) -> AsyncIterator[None]:
    print("lifespan: startup")
    app.state.resource = Resource()
    try:
        yield
    finally:
        app.state.resource.close()
        print("lifespan: shutdown")


app = FastAPI(lifespan=lifespan)


@app.get("/use-resource")
async def use_resource(request: Request) -> dict[str, str]:
    print("endpoint: запрос")
    result = request.app.state.resource.use()
    return {"result": result}


with TestClient(app) as client:
    print("test: первый запрос")
    print(client.get("/use-resource").json())

    print("test: второй запрос")
    print(client.get("/use-resource").json())

print("test: контекст закрыт")
```

`TestClient` используется как context manager, чтобы startup и shutdown lifespan действительно выполнились.
