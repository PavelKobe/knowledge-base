# M00.8.1a — TOML и pyproject.toml с нуля

## Зачем нужен этот урок

В M00.8.1 понадобилось изменить `pyproject.toml`: перенести `httpx` из dev-зависимостей в runtime-зависимости. Чтобы это не было механическим редактированием незнакомого файла, разберём:

- что такое конфигурационный файл;
- как устроен TOML;
- как TOML превращается в Python-структуры;
- какую роль выполняет `pyproject.toml`;
- чем runtime-зависимости отличаются от dev-зависимостей;
- как безопасно изменять TOML и находить ошибки.

После урока вы должны уметь открыть незнакомый TOML-файл, прочитать его структуру и объяснить каждое изменение до его выполнения.

---

## 1. Что такое конфигурация

Программа состоит не только из алгоритмов. Ей также нужны настройки:

- имя и версия проекта;
- минимальная версия Python;
- список библиотек;
- правила линтера;
- расположение тестов;
- параметры сборки пакета.

Эти сведения можно было бы записать прямо в Python-коде, но тогда инструменты установки и сборки должны были бы исполнять этот код. Это сложнее и опаснее.

Конфигурационный файл хранит **данные о том, как другой инструмент должен работать**. TOML не является программой: в нём нет циклов, функций и `if`. Он только описывает значения и их структуру.

Простая модель:

```text
Python-файл → команды, которые исполняются
TOML-файл   → данные, которые читаются инструментом
```

## 2. Что означает TOML

TOML — текстовый формат конфигурации. Его основная идея: файл должен быть достаточно строгим для компьютера и достаточно понятным для человека.

TOML-документ состоит из:

1. ключей;
2. значений;
3. таблиц, которые группируют связанные ключи.

Минимальный пример:

```toml
name = "interviewlab"
version = "0.1.0"
debug = false
workers = 4
```

Слева находится ключ, справа — значение.

Если прочитать такой TOML из Python, мысленно его можно представить как словарь:

```python
{
    "name": "interviewlab",
    "version": "0.1.0",
    "debug": False,
    "workers": 4,
}
```

Важно: это только мысленная модель. Сам TOML не является Python-кодом.

---

## 3. Основные типы значений

### 3.1. Строка

```toml
name = "interviewlab"
```

Обычная строка заключается в кавычки. Без кавычек `interviewlab` не будет строковым значением.

### 3.2. Целое и вещественное число

```toml
workers = 4
timeout = 5.0
```

Это числа, поэтому кавычки не нужны. Значение `"4"` было бы строкой, а не числом.

### 3.3. Логическое значение

```toml
debug = false
enabled = true
```

Используются строчные `true` и `false`. Это не строки, поэтому кавычки не ставятся.

### 3.4. Массив

```toml
tags = ["backend", "fastapi", "asyncio"]
```

Массив соответствует идее Python-списка. Элементы разделяются запятыми.

Многострочная запись удобнее для зависимостей:

```toml
dependencies = [
    "fastapi>=0.115,<1.0",
    "httpx>=0.27,<1.0",
]
```

Запятая после последнего элемента разрешена и уменьшает размер будущих изменений в Git.

### 3.5. Комментарий

```toml
# Этот текст игнорируется TOML-парсером
workers = 4  # Комментарий также может стоять после значения
```

Комментарий начинается с `#` и действует до конца строки.

## 4. Таблицы: аналог вложенного словаря

Заголовок в квадратных скобках создаёт таблицу:

```toml
[server]
host = "127.0.0.1"
port = 8000
```

Мысленная Python-модель:

```python
{
    "server": {
        "host": "127.0.0.1",
        "port": 8000,
    }
}
```

Вложенная таблица задаётся точкой:

```toml
[server.logging]
level = "INFO"
json = true
```

Теперь `logging` находится внутри `server`.

Главное правило чтения: после `[server]` все следующие пары `ключ = значение` принадлежат этой таблице, пока не встретится новый заголовок таблицы.

## 5. Массив таблиц

Двойные квадратные скобки означают не одну таблицу, а очередной элемент списка таблиц:

```toml
[[services]]
name = "api"
port = 8000

[[services]]
name = "worker"
port = 8001
```

Мысленная модель:

```python
{
    "services": [
        {"name": "api", "port": 8000},
        {"name": "worker", "port": 8001},
    ]
}
```

Не путайте:

```text
[service]   → один словарь service
[[service]] → список, содержащий несколько service
```

## 6. Что такое pyproject.toml

`pyproject.toml` — стандартная точка конфигурации современного Python-проекта. Один файл могут читать разные инструменты:

```text
pyproject.toml
├── система сборки
├── установщик пакетов
├── pytest
├── Ruff
└── mypy
```

Каждый инструмент читает только известную ему секцию.

## 7. Разбор pyproject.toml проекта InterviewLab

### 7.1. Система сборки

```toml
[build-system]
requires = ["hatchling>=1.25"]
build-backend = "hatchling.build"
```

Эта секция отвечает на два вопроса:

1. что установить, чтобы собрать проект;
2. какой компонент выполнить для сборки.

`hatchling` здесь не является библиотекой бизнес-логики FastAPI. Это инструмент упаковки проекта.

### 7.2. Описание проекта

```toml
[project]
name = "interviewlab"
version = "0.1.0"
requires-python = ">=3.12"
```

Таблица `[project]` содержит метаданные устанавливаемого Python-пакета.

`requires-python = ">=3.12"` означает: установщик должен отказать, если Python старше по номеру недостаточно, например Python 3.11.

### 7.3. Runtime-зависимости

```toml
dependencies = [
    "fastapi>=0.115,<1.0",
    "uvicorn[standard]>=0.30,<1.0",
    "httpx>=0.27,<1.0",
]
```

Это библиотеки, без которых установленное приложение не сможет нормально работать.

Проверочный вопрос для каждой зависимости:

> Может ли production-код импортировать или использовать эту библиотеку во время запуска и обработки запросов?

Если да — это runtime-зависимость.

### 7.4. Дополнительная группа dev

```toml
[project.optional-dependencies]
dev = [
    "pytest>=8.3,<9.0",
    "ruff>=0.8,<1.0",
    "mypy>=1.13,<2.0",
]
```

`dev` — имя дополнительного набора. Эти инструменты нужны разработчику, но production-приложение не импортирует их для обработки запроса.

Команда:

```powershell
python -m pip install -e ".[dev]"
```

означает:

- `.` — установить текущий проект;
- `-e` — editable-режим: изменения исходников видны без повторной установки;
- `[dev]` — дополнительно установить группу `dev`.

Production-установка без dev-инструментов могла бы выглядеть так:

```powershell
python -m pip install .
```

### 7.5. Настройки отдельных инструментов

```toml
[tool.pytest.ini_options]
testpaths = ["tests"]
```

Это настройки pytest.

```toml
[tool.ruff]
target-version = "py312"
line-length = 100

[tool.ruff.lint]
select = ["E", "F", "I", "UP", "B", "ASYNC"]
```

Это две связанные, но разные таблицы: общие настройки Ruff и вложенные настройки его линтера.

```toml
[tool.mypy]
python_version = "3.12"
strict = true
```

Это настройки статической проверки типов.

## 8. Как читать ограничения версий

Пример:

```text
fastapi>=0.115,<1.0
```

Он означает одновременно:

- установить версию не ниже `0.115`;
- не устанавливать версию `1.0` или выше.

Запись ограничивает допустимый диапазон:

```text
0.115 ≤ версия < 1.0
```

Зачем верхняя граница: следующая крупная версия может содержать несовместимые изменения.

Пример с extra:

```text
uvicorn[standard]>=0.30,<1.0
```

`uvicorn` — пакет, а `[standard]` — дополнительный набор возможностей самого Uvicorn. Это не наша группа `[dev]`; синтаксис похож, но контекст различается.

## 9. Почему зависимость нельзя без причины дублировать

Если `httpx` записан и в `dependencies`, и в `dev`, установка обычно не сломается: установщик объединит ограничения. Но файл начинает сообщать две разные истории об одной библиотеке.

Проблемы дублирования:

- непонятно, к какой категории относится библиотека;
- ограничения версий могут со временем разойтись;
- review становится сложнее;
- человек может изменить одну запись и забыть вторую.

Правильная модель для InterviewLab:

```text
httpx → runtime, потому что импортируется lifecycle.py
pytest → dev, потому что запускает тесты
ruff → dev, потому что проверяет стиль
mypy → dev, потому что проверяет типы
```

## 10. Три разных класса ошибок

### 10.1. Синтаксическая ошибка TOML

```toml
workers = 4
name = "api
```

Строковая кавычка не закрыта, поэтому файл нельзя разобрать.

### 10.2. TOML корректен, но значение неверного типа

```toml
[tool.ruff]
line-length = "сто"
```

Для TOML это допустимая строка. Но Ruff ожидает число и отклонит настройку.

### 10.3. TOML корректен, но инструмент не знает ключ

```toml
[tool.ruff]
line-lenght = 100
```

Опечатка не нарушает грамматику TOML. Ошибку должен обнаружить Ruff, потому что только Ruff знает имена своих параметров.

Отсюда важный вывод:

```text
TOML-парсер проверяет форму данных.
Конкретный инструмент проверяет смысл данных.
```

## 11. Метод безопасного изменения pyproject.toml

Перед изменением выполните пять шагов.

### Шаг 1. Назовите владельца секции

Например, `[tool.ruff]` читает Ruff, а `[project]` читает система упаковки Python.

### Шаг 2. Определите тип данных

Вы меняете строку, число, флаг, массив или таблицу?

### Шаг 3. Сформулируйте смысл изменения

Не «переношу строку», а «объявляю `httpx` обязательной библиотекой работающего приложения».

### Шаг 4. Измените одно логическое место

Не смешивайте перенос зависимости, перенастройку Ruff и обновление версии проекта без необходимости.

### Шаг 5. Проверьте два уровня

1. файл разбирается как TOML;
2. инструмент принимает свою конфигурацию.

Проверка синтаксиса стандартной библиотекой Python 3.11+:

```powershell
python -c "import tomllib; tomllib.load(open('pyproject.toml', 'rb')); print('TOML syntax: OK')"
```

После этого запускают конкретные инструменты:

```powershell
python -m pip install -e ".[dev]"
python -m pytest -q
python -m ruff check src
python -m mypy src
```

## 12. Чтение TOML из Python

Начиная с Python 3.11, стандартная библиотека содержит `tomllib`:

```python
from pathlib import Path
import tomllib

with Path("pyproject.toml").open("rb") as file:
    config = tomllib.load(file)

project_name = config["project"]["name"]
print(project_name)
```

Почему файл открыт как `rb`: `tomllib.load()` принимает бинарный файловый объект и самостоятельно обрабатывает требуемую кодировку TOML.

`tomllib` только читает TOML. Для изменения обычно используют специализированную библиотеку или аккуратно редактируют файл как конфигурацию. На данном этапе автоматическая запись TOML нам не нужна.

## 13. Словарь урока

| Термин | Простое объяснение |
|---|---|
| конфигурация | данные, управляющие поведением инструмента или программы |
| парсер | код, превращающий текст TOML во внутреннюю структуру данных |
| ключ | имя настройки слева от `=` |
| значение | данные справа от `=` |
| таблица | именованная группа связанных настроек |
| runtime dependency | библиотека, необходимая работающему приложению |
| dev dependency | инструмент, необходимый разработке или проверке |
| extra | дополнительный именованный набор зависимостей |
| build backend | инструмент, собирающий Python-пакет |
| metadata | данные, описывающие проект: имя, версия, требования |

## 15. Небольшая практика

Создайте в `backend/task` файл `toml_lab.toml`. Не копируйте готовое решение: составьте структуру самостоятельно по требованиям.

В файле должны быть:

1. таблица `[student]` с ключами `name`, `module` и `completed`;
2. `completed` должен быть логическим значением, а не строкой;
3. массив `topics` минимум из трёх строк;
4. вложенная таблица `[student.environment]` с версиями Python и редактором;
5. два элемента `[[dependencies]]`;
6. у каждой зависимости должны быть `name` и `scope`;
7. одна зависимость должна иметь scope `runtime`, вторая — `dev`.

Проверьте синтаксис:

```powershell
python -c "import tomllib; tomllib.load(open('task/toml_lab.toml', 'rb')); print('TOML syntax: OK')"
```

Затем прочитайте получившуюся структуру:

```powershell
python -c "import pprint, tomllib; pprint.pp(tomllib.load(open('task/toml_lab.toml', 'rb')))"
```
