## Карта концепций

### Контракт

1. **REST** — методы действуют над ресурсами: `GET /users/42`.
2. **Пагинация** — большие коллекции отдаются порциями через `limit` и `cursor`.
3. **Версионирование** — `/v1` и `/v2` живут одновременно во время миграции.
4. **GraphQL** — клиент запрашивает только нужные поля.
5. **Auth + scopes** — `401` означает отсутствие аутентификации, `403` — нехватку прав.
6. **Status codes** — коды ответа служат инструкциями клиенту, а не декорацией.

### Доставка

7. **Webhooks** — внешний сервис сам вызывает endpoint приложения.
8. **gRPC** — типизированные бинарные сообщения и стримы поверх HTTP/2.

### Устойчивость

9. **Идемпотентность** — один ключ создаёт один результат даже при повторе запроса.
10. **Rate limits** — бюджет запросов защищает сервис; `429` дополняется `Retry-After`.
11. **Retries** — повторы используют exponential backoff и jitter.
12. **Timeouts** — каждый сетевой вызов имеет ограниченный бюджет ожидания.

## Главная причинно-следственная цепочка

```text
запрос завис
  → сработал timeout
    → клиент сделал retry
      → первый запрос мог уже выполниться
        → idempotency не даёт создать дубль
          → rate limit сдерживает массовые повторы
```

Timeout, retry, idempotency и rate limit нельзя проектировать независимо. Timeout говорит только о том, что клиент перестал ждать. Он не доказывает, что сервер не выполнил операцию. Поэтому повтор должен быть безопасным, рассредоточенным во времени и ограниченным по частоте.

## Правила, которые стоит унести

- Retry без jitter создаёт синхронную волну запросов и может повторно положить сервис.
- `429 + Retry-After` сообщает клиенту, когда можно вернуться.
- `503` обычно допускает retry, `400` — нет: запрос нужно исправить.
- `200 OK` с полем `error` ломает стандартную семантику клиентов, proxy и мониторинга.
- Для денежных и создающих операций `Idempotency-Key` должен быть частью контракта.
- Дедлайн должен передаваться вниз по цепочке, а отмена — освобождать ресурсы.
