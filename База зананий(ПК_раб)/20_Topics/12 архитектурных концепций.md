## Общая карта

```text
User
  → CDN
    → API Gateway
      → Rate Limiter
        → Cache
          → Load Balancer
            → Service Discovery
              → Service
                → Shard
```

Асинхронный контур дополняет основной путь:

```text
Service → Message Queue / Topic → Consumers
                  ↓
            retry · DLQ · replay
```

## 12 концепций

### Управление трафиком

1. **Load Balancing** распределяет запросы между здоровыми экземплярами.
2. **Caching** снимает повторные чтения с медленного источника.
3. **CDN** отдаёт контент с ближайшей edge-точки.
4. **API Gateway** создаёт единую границу маршрутизации, auth и политик.

### Устойчивость

5. **Circuit Breaker** останавливает вызовы падающей зависимости и предотвращает каскадный отказ.
6. **Rate Limiting** защищает ограниченную ёмкость от одного клиента, атаки или retry storm.
7. **Auto Scaling** меняет число экземпляров вслед за устойчивым спросом.

### Данные

8. **Sharding** горизонтально разделяет набор данных по partition key.
9. **Consistent Hashing** уменьшает число перемещаемых ключей при изменении состава кластера.

### Связи и асинхронность

10. **Message Queue** отделяет скорость producer от скорости consumer.
11. **Publish–Subscribe** доставляет одно событие нескольким независимым подписчикам.
12. **Service Discovery** превращает имя сервиса в актуальный адрес здорового экземпляра.

## Как выбирать концепцию

| Симптом | Начать с | Не забыть |
|---|---|---|
| Один сервер перегружен | Load Balancing | health checks, stateless sessions |
| БД повторяет одинаковые чтения | Caching | TTL, invalidation, stampede protection |
| Большая задержка для удалённых пользователей | CDN | cache headers, purge, приватность |
| Пики ломают downstream | Message Queue | idempotent consumer, retries, DLQ |
| Несколько реакций на одно событие | Pub/Sub | schema evolution, replay, порядок |
| Падает зависимость и тянет остальных | Circuit Breaker | timeout, fallback, half-open |
| Одна БД достигла предела | Sharding | выбор ключа, resharding, cross-shard queries |
| Изменяется состав кэш-кластера | Consistent Hashing | virtual nodes, hot keys |
| Нагрузка сильно меняется | Auto Scaling | метрика спроса, cooldown, запас запуска |

## Важные связи

- **Load Balancing + Service Discovery + Auto Scaling**: новый экземпляр должен появиться, зарегистрироваться и начать получать трафик только после readiness check.
- **Timeout + Circuit Breaker + Retry**: timeout ограничивает ожидание, breaker останавливает бесполезные вызовы, retry должен иметь backoff и jitter.
- **Queue + Idempotency + DLQ**: сообщение может прийти повторно; consumer обязан быть идемпотентным, а необрабатываемые события уходят в DLQ.
- **Sharding + Consistent Hashing**: оба распределяют данные, но consistent hashing прежде всего уменьшает remapping при изменении числа узлов.
- **Gateway + Rate Limit + Auth**: политики удобно применять на границе, но проверка доступа к конкретному объекту остаётся в сервисе.

## Главный принцип

Архитектурный компонент нужен не потому, что он встречается на диаграммах. Он нужен, когда есть измеримый поток или риск, которым требуется управлять: запросы, задержка, нагрузка, события, ошибки, данные или изменение состава кластера.
