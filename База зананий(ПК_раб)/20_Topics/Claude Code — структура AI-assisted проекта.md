# Claude Code — структура AI-assisted проекта

Практическая схема организации проекта, в котором AI-агент регулярно пишет, проверяет и сопровождает код. Главная идея: по мере роста проекта узким местом становится не генерация кода, а управление контекстом, командами, skills, hooks, субагентами, MCP-интеграциями и проверками.

> [!info] Карта экосистемы
> [[Claude — карта возможностей]] — когда использовать Artifacts, Skills, Connectors, Claude Code, MCP, Projects и Automation.

> [!important] Область применения
> Имена `CLAUDE.md` и `.claude/` относятся к Claude Code. Сами принципы переносятся на другие агентные среды. Для Codex роль корневых инструкций обычно выполняет `AGENTS.md`, а повторяемые процессы оформляются как skills, плагины, команды проекта и автоматические проверки.

## Базовая структура

```text
my-project/
├── CLAUDE.md                 # краткие правила и контекст проекта
├── .claude/
│   ├── settings.json         # общие настройки команды
│   ├── settings.local.json   # локальные настройки, не коммитить
│   ├── commands/             # повторяемые slash-команды
│   │   ├── review.md
│   │   ├── deploy.md
│   │   ├── test-all.md
│   │   └── bootstrap.md
│   ├── skills/               # предметные рабочие процессы
│   │   ├── code-review/
│   │   │   ├── SKILL.md
│   │   │   ├── scripts/
│   │   │   ├── references/
│   │   │   └── assets/
│   │   ├── test-writer/
│   │   │   └── SKILL.md
│   │   └── security-audit/
│   │       └── SKILL.md
│   ├── agents/               # узкие роли субагентов
│   │   ├── code-reviewer.yml
│   │   ├── test-writer.yml
│   │   └── security-auditor.yml
│   └── plugins/              # локальные расширения проекта
├── .mcp.json                 # определения MCP-серверов
├── src/                      # продуктовый код
├── tests/                    # unit / integration / e2e
├── docs/                     # архитектура, API, onboarding, решения
├── scripts/                  # setup, test, deploy, seed
├── .env.example              # только имена переменных и безопасные примеры
├── .gitignore
└── README.md
```

Структура не является обязательным стандартом. Добавлять каталог следует только тогда, когда появился реальный повторяемый процесс или отдельная ответственность.

## Роли ключевых компонентов

| Компонент | Ответственность | Что нельзя туда складывать |
|---|---|---|
| `CLAUDE.md` | архитектура, команды, соглашения, запреты | длинные справочники, секреты, временные задачи |
| `.claude/settings.json` | разделяемая конфигурация команды | персональные пути и токены |
| `.claude/settings.local.json` | локальные разрешения и предпочтения | данные, которые нужны коллегам или CI |
| `commands/` | короткие пользовательские команды | сложную логику без проверок и документации |
| `skills/` | повторяемый workflow с инструкциями и ресурсами | одноразовые промпты |
| `agents/` | узкие изолированные роли | неограниченного «универсального исполнителя» |
| `.mcp.json` | подключение внешних инструментов | избыточные разрешения и открытые секреты |
| `docs/` | долговечные знания и решения | дублирование корневых инструкций |

## Что должно быть в `CLAUDE.md`

Корневой файл остаётся коротким источником истины и отвечает на пять вопросов:

1. Какой стек и как устроены границы модулей?
2. Какие команды запускают приложение и проверки?
3. Какие соглашения по коду уже приняты?
4. Как устроены тесты, ветки и рабочий процесс?
5. Какие правила безопасности и compliance нельзя нарушать?

Хороший файл ссылается на подробные документы, а не копирует их. Практический предел зависит от проекта, но сотни строк инструкций обычно сигнализируют, что справочные материалы пора вынести в `docs/` или `references/`.

## Skills

Минимальная структура одного skill:

```text
skill-name/
├── SKILL.md       # назначение, триггер, процесс, критерии готовности
├── scripts/       # детерминированная автоматизация
├── references/    # справка, загружаемая по необходимости
└── assets/        # шаблоны и статические файлы
```

Правило разделения ответственности:

- `SKILL.md` объясняет **когда и как** выполнять процесс;
- `scripts/` выполняет детерминированные операции;
- `references/` хранит подробности, которые не нужны в каждом запуске;
- `assets/` содержит переиспользуемые шаблоны результата.

## Hooks

Hooks полезны там, где правило должно срабатывать детерминированно, а не зависеть от решения модели.

| Событие | Практическое применение |
|---|---|
| До вызова инструмента | блокировать опасные команды и выход за разрешённую область |
| После записи файла | запускать formatter, lint или точечную проверку |
| Начало сессии | загружать минимальный актуальный контекст |
| Конец сессии | сохранять краткий отчёт и незавершённые вопросы |
| Перед коммитом | искать секреты и запускать обязательный набор проверок |
| Уведомление | сообщать о сбое длительного фонового процесса |

Не превращать hooks в скрытую бизнес-логику. Они должны быть быстрыми, наблюдаемыми и безопасно повторяемыми.

## Повторяемые команды

Имеет смысл стандартизировать операции, которые команда выполняет постоянно:

- `review` — проверить diff и выдать замечания по приоритетам;
- `test-all` — запустить полный набор тестов;
- `bootstrap` — подготовить новый модуль по принятому шаблону;
- `document` — обновить документацию затронутого контракта;
- `refactor` — предложить улучшение без изменения поведения;
- `deploy` — собрать артефакт и подготовить staging-проверку.

Разрушительные или внешние действия не должны скрываться за неясным именем команды. Публикация, production deploy и изменение данных требуют отдельного явного шага и подтверждения.

## Паттерны работы нескольких агентов

| Паттерн | Когда применять | Риск |
|---|---|---|
| Orchestrator | есть несколько независимых специализаций | центральный агент становится узким местом |
| Pipeline | результат одного этапа нужен следующему | ранняя ошибка распространяется по цепочке |
| Map–Reduce | независимый параллельный анализ с последующим синтезом | дублирование и конфликт выводов |
| Supervisor | длительные задачи требуют контроля и повторов | лишняя сложность для короткой работы |
| Swarm | состав задач заранее неизвестен | сложно контролировать область и стоимость |

Перед делегированием определить: вход, ожидаемый результат, область файлов, критерий завершения и владельца интеграции. Параллельные исполнители не должны редактировать одни и те же файлы.

## Управление контекстом

Контекст — ограниченный рабочий ресурс. Универсальная стратегия:

- в начале работать свободно, но не загружать нерелевантные файлы;
- при заметном росте отделять факты от временных наблюдений;
- до переполнения сохранять решения, статус и открытые вопросы в коротком summary;
- после compaction проверять актуальную задачу и не повторять завершённую работу;
- начинать чистую сессию, если старый контекст создаёт больше шума, чем пользы.

Указанные в исходной схеме пороги заполнения контекста полезны как сигнал, но не как строгий стандарт: доступный объём и поведение compaction различаются между инструментами и моделями.

## Безопасность

- [ ] Секреты никогда не хранятся в `CLAUDE.md`, skills, промптах и логах.
- [ ] В репозитории есть только `.env.example` с безопасными заглушками.
- [ ] Локальные настройки добавлены в `.gitignore`.
- [ ] Pre-commit или CI выполняет secret scanning.
- [ ] MCP-серверам выданы минимальные разрешения.
- [ ] Запись, публикация и удаление отделены от чтения.
- [ ] Внешний контент считается недоверенным и не может переопределить правила проекта.
- [ ] Все автоматические действия оставляют понятный журнал.

## Антипаттерны

| Антипаттерн | Последствие | Исправление |
|---|---|---|
| Огромный `CLAUDE.md` | постоянное загрязнение контекста | вынести подробности в `docs/` и references |
| «Пиши хороший код» | непроверяемое требование | дать конкретные правила и команды проверки |
| Дублирование документации | противоречащие источники истины | хранить факт в одном месте, в остальных ставить ссылки |
| Нет обязательных тестов | агент пропускает проверку | определить минимальный набор и запускать автоматически |
| Ошибки без классификации | каждый модуль обрабатывает сбой иначе | задать единый error pattern |
| Skills как длинные промпты | процессы нельзя воспроизвести | вынести детерминированные шаги в scripts |
| Субагенты без границ | конфликты файлов и непроверяемый результат | ограничить область и формат передачи |

## Порядок внедрения

1. Создать короткий `CLAUDE.md` или `AGENTS.md` с командами, архитектурой и запретами.
2. Зафиксировать стабильный набор `dev`, `test`, `lint`, `typecheck`, `check`.
3. Добавить `docs/architecture.md`, `docs/api.md` и журнал решений только при реальной необходимости.
4. Оформить первую повторяемую операцию как команду или skill.
5. Добавить hooks для форматирования, тестов и secret scanning.
6. Подключать MCP по одному, начиная с минимальных прав.
7. Добавлять субагентов только для независимой параллельной работы.
8. Регулярно удалять устаревшие инструкции и проверять свежий clone проекта.

## Адаптация для Codex

| Claude Code | Переносимый эквивалент в Codex |
|---|---|
| `CLAUDE.md` | `AGENTS.md` |
| `.claude/skills/` | Codex skills с `SKILL.md` |
| `.claude/commands/` | команды проекта, skills или повторяемые task-инструкции |
| agents | субагенты с ограниченной задачей и областью файлов |
| plugins | Codex plugins и их skills/MCP/apps |
| `.mcp.json` | подключённые MCP-серверы и приложения |
| hooks | hooks проекта, pre-commit, CI и детерминированные проверки |
